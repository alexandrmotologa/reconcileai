# reconcileai: Architecture and Engineering Master Plan
> Autonomous 3-Way Document Matching & Discrepancy Auditor for Enterprise Accounts Payable
> Target: Single-Binary Go Engine (< 25MB RAM) with Embedded React 19 Discrepancy Cockpit & ERP Settlement Export

---

## 1. Problem Statement and Motivation

### 1.1 The Expensive Bottleneck of Manual 3-Way Invoice Matching
In enterprise accounting and procurement departments, the Accounts Payable (AP) team spends massive human effort performing "3-Way Matching"—the mandatory internal control process that verifies financial obligations before releasing funds to suppliers:
1. **The Tripartite Paperwork Dilemma**: Every transaction involves three distinct, heterogeneous documents originating from different sources:
   - **The Purchase Order (PO)**: Generated internally by procurement, detailing authorized items, quantities, agreed unit prices, and payment terms.
   - **The Goods Receipt / Delivery Note (GRN)**: Generated by the warehouse upon physical intake, detailing actual received units, backordered items, and damaged goods.
   - **The Supplier Invoice (INV)**: Sent by the external vendor, requesting payment with applied taxes, freight surcharges, and currency rates.
2. **High Error Rates and Silent Overbilling**: Human accountants manually comparing 50-line tables across PDFs and scans frequently overlook subtle overbilling: suppliers charging \$12.50 per unit instead of the agreed \$11.80, billing for 100 units when only 80 were delivered, or tacking on unapproved "freight handling" fees.
3. **Mismatched SKU and Naming Conventions**: Vendors rarely use the buyer's internal part numbers (e.g., Buyer PO: `PART-902-BLU`; Vendor Invoice: `M-Widget Steel (Blue Finish, 10mm)`), rendering standard database string lookups completely ineffective.
4. **Delayed Vendor Payments and Lost Early-Pay Discounts**: Manual invoice review queues take an average of 14 to 21 days per invoice cycle, forfeiting 2/10 Net 30 early payment cash discounts and straining supplier relationships.

### 1.2 The reconcileai Solution
`reconcileai` is an autonomous enterprise document reconciliation engine written in Go. Operating locally on CPU without heavy cloud dependencies:
- **Multimodal Document Table Extraction**: Ingests raw PDFs, scans, and structured EDI/JSON records, extracting line-item tables with column semantics (SKU, description, unit price, quantity, tax, total).
- **Semantic SKU & Entity Alignment**: Employs hybrid embeddings and fuzzy string heuristics to deterministically map vendor invoice descriptions to internal PO line items.
- **Mathematical 3-Way Discrepancy Engine**: Evaluates strict business invariant rules:
  - $\text{Quantity Check}$: $\text{Qty}_{\text{Invoiced}} \le \text{Qty}_{\text{Received}} \le \text{Qty}_{\text{Ordered}}$.
  - $\text{Price Tolerance Check}$: $|\text{Price}_{\text{Invoiced}} - \text{Price}_{\text{PO}}| \le \epsilon_{\text{contract}}$.
  - $\text{Tax and Surcharge Verification}$: Audits calculated sales tax/VAT percentages and flags unapproved line items.
- **Visual Evidence Grounding**: Links every identified discrepancy directly to its bounding coordinates on the original PDF pages, providing 1-click audit verification.
- **Automated ERP Settlement Dispatch**: If all checks pass, generates certified settlement payloads for SAP (IDoc), NetSuite (CSV), and QuickBooks (JSON); if discrepancies are detected, routes them to an interactive human-in-the-loop approval cockpit.

## 3. Mathematical Verification and Invariant Rules

```
+-----------------------------------+-----------------------------------------------------------------+
| Verification Rule                 | Mathematical Formulation & Invariant                            |
+-----------------------------------+-----------------------------------------------------------------+
| 1. Quantity Invariant             | $Q_{\text{inv}} \le Q_{\text{rec}} \le Q_{\text{po}}$          |
|                                   | Flag if billed quantity exceeds verified warehouse intake.      |
| 2. Price Tolerance Bound          | $\Delta P = P_{\text{inv}} - P_{\text{po}} \le \theta_{\text{p}}|
|                                   | Flag if unit price exceeds PO price beyond contract tolerance.  |
| 3. Line-Item Mathematical Sum     | $\sum (Q_i \cdot P_i) + \text{Tax} + \text{Freight} = \text{Total}|
|                                   | Flag internal arithmetic errors on invoice face.                |
| 4. Surcharge Authorization        | $\forall s \in \text{Surcharges}_{\text{inv}}: s \in \text{PO}_{\text{terms}}$ |
|                                   | Flag unexpected handling, packing, or rush delivery fees.       |
| 5. Duplicate Invoicing Check      | $\text{Hash}(\text{VendorID}, \text{InvNum}) \notin \text{Ledger}|
|                                   | Prevent double payment of previously settled invoices.          |
+-----------------------------------+-----------------------------------------------------------------+
```

## 5. Implementation Roadmap

### Phase 1: Go Engine Setup and PDF Table Extractor
- Initialize Go module with minimal dependencies.
- Build PDF text and table layout parser in `internal/ingestion/table_extractor.go` extracting rows, cells, and bounding coordinates.
- Implement data structures for PO, Delivery Note, and Vendor Invoice documents.

### Phase 2: Fuzzy SKU and Line-Item Alignment
- Implement bipartite matching in `internal/matching/line_pairing.go` pairing invoice rows with PO rows using Jaro-Winkler description similarity and token overlap.
- Handle vendor unit of measure conversions (e.g. dozens $\leftrightarrow$ single units, kg $\leftrightarrow$ lbs).

### Phase 3: Mathematical 3-Way Auditor
- Implement quantity validation checking invoice lines against physical goods receipt logs.
- Implement unit price variance auditing against agreed purchase order contracts with configurable percentage tolerances ($\pm 0.5\%$).
- Implement arithmetic total validation verifying that $\sum(\text{Qty} \times \text{Price}) + \text{Tax} + \text{Freight} = \text{Total}$.

### Phase 4: Visual Evidence Annotator and Dispute Memo
- Build PDF annotator drawing red bounding rectangles and numbered callout badges directly onto original document pages where discrepancy figures reside.
- Generate structured Vendor Dispute Memos detailing exact variances with attached annotated page excerpts.

### Phase 5: ERP Export Dispatchers
- Implement SAP S/4HANA IDoc XML generator for automated settlement clearance.
- Implement NetSuite CSV and QuickBooks Online JSON payment payload builders.

### Phase 6: Embedded React 19 Discrepancy Cockpit
- Develop AP cockpit in `web/` using React 19, Tailwind CSS, and Lucide icons.
- Build 3-way side-by-side comparison table with highlighted variance cells and interactive PDF viewer.
- Embed frontend static assets into Go binary via `//go:embed` and serve locally on `:7272`.

### Phase 7: Verification, Benchmarking, and Documentation
- Run test cases on `examples/test_dossiers` verifying 100% detection of quantity overbilling and unauthorized surcharges.
- Benchmark processing speed ensuring a 3-document transaction set reconciles in $< 250\text{ms}$.
- Author humanized README with setup guides, ERP mapping templates, and enterprise AP security guidelines.
